🏭 Warehouse Refund Processing System

A production-grade, multi-agent AI system built with LangGraph, FastAPI, and Groq LLMs to autonomously process warehouse refund requests with full crash recovery, human oversight, and audit compliance.

System Overview

This system automates warehouse refund processing using a multi-agent AI workflow. When a customer submits a refund request via REST API, the system orchestrates three specialized AI agents — Validation, Policy, and Communication — each powered by a Groq LLM using the ReAct (Reasoning + Acting) pattern with database and vector tools.

🎯 Purpose

Automate warehouse refund decisions: validate customer/order data, check warehouse return policies, calculate refund amounts by tier, persist decisions, and route ambiguous cases to human review.

🏗️ Core Architecture

Supervisor-pattern multi-agent LangGraph workflow. A supervisor LLM routes between agents. Each agent uses ReAct to call tools in parallel waves. Checkpoints survive crashes.

⚡ Key Properties

  • Async throughout (FastAPI + asyncio)
  • Idempotent: duplicate requests safely detected
  • Crash-safe: tasks resume from last checkpoint
  • HITL: escalates to human when AI is unsure
  • Full audit trail + telemetry

System Architecture

Supervisor-Pattern Multi-Agent Design

The workflow is a directed state graph (LangGraph StateGraph) with a central supervisor that uses LLM tool-calling to decide which agent runs next. There is no hardcoded routing logic — the LLM reasons from the current state fields.

LangGraph Graph Topology

START → supervisor → [validation | policy | communication | hitl]
         ↑___________↙ (agents return to supervisor after each step)
         hitl → END

Every agent node feeds back to the supervisor. The supervisor re-evaluates state after each step and calls exactly one routing tool to express its next decision.

RefundState — Shared Workflow State

All agents read from and write into a RefundState TypedDict. LangGraph merges each agent's returned dict back into the shared state using operator.add for message lists.

Key State Fields

Field Set By Purpose
validation_passed Validation Agent Supervisor routing pivot: None→validate, False→end, True→policy
decision Policy Agent "approved" or "denied" — pivot for communication routing
request_saved Communication Agent True when all DB writes done → supervisor calls finish_workflow
hitl_required Any agent / Supervisor Supervisor sees this first; bypasses normal routing → HITL node
cycle_count Supervisor Incremented each pass; cap at 15 → auto-HITL
agent_retry_counts Supervisor Per-agent counter; cap at 3 → auto-HITL
thread_id main.py UUID of the task; used as LangGraph config key and checkpoint key

Checkpoint-Aware Node Wrappers

Each agent node is wrapped in a thin async function (_validation_node, _policy_node, _communication_node) that calls the real agent, then calls _save() to persist a checkpoint to Redis + PostgreSQL. This is separate from LangGraph's own internal checkpointer.

Complete Request Lifecycle (Happy Path)

Client sends POST /refund

Payload: customer_email, order_id, refund_reason, optional idempotency_key

Idempotency check (dual-layer)

Compute key = client key or sha256(email:order:reason). Check Redis first (<1ms). If miss, check PostgreSQL IdempotencyRecord. If both miss → new request.

Write IdempotencyRecord to DB + cache in Redis

DB write is first (durable). IntegrityError on race condition safely handled. Then Redis cache set with 24h TTL.

Enqueue task in Redis persistent queue

HSET the payload to refund:tasks hash; SADD task_id to refund:tasks:pending set. This enables crash recovery on restart.

Return task_id immediately to client

API returns {"task_id": "...", "status": "processing"}. Client polls GET /refund/{task_id}.

FastAPI BackgroundTask runs _process_refund()

Marks queue entry as "processing". Binds task_id + order_id to structlog context vars for all log lines.

LangGraph workflow starts: Supervisor → Validation Agent

Supervisor LLM sees validation_passed=None, calls call_validation_agent tool. Validation agent runs ReAct loop: Wave 0 (lookup_customer + get_order_details in parallel) → Wave 1 (get_customer_analytics + verify_order_ownership in parallel). Returns structured JSON decision. Checkpoint saved to Redis + PG.

Supervisor → Policy Agent

Supervisor sees validation_passed=True, decision=None, calls call_policy_agent. Policy agent runs 7-tool Wave 0 (search_policies, check_refund_history, check_eligibility, get_product_return_policy, get_customer_order_summary, get_refund_rate_by_category, get_similar_refund_decisions) then Wave 1 (calculate_refund — needs eligibility result). search_policies hits Pinecone via semantic cache. Returns approved/denied decision with refund amount. Checkpoint saved.

Supervisor → Communication Agent

Supervisor sees decision set, request_saved≠True, calls call_communication_agent. All 4 tools run in parallel (single wave): save_processed_request (upsert + dedup), update_customer_analytics (idempotent per refund_request_id), update_refund_request_status, log_audit_event. Returns JSON with all flags true. Checkpoint saved.

Supervisor calls finish_workflow

Sees request_saved=True. Returns "end". LangGraph routes to END.

Results written to 3-layer storage

Redis: full JSON with TTL 1h. PostgreSQL TaskResult: permanent record. IdempotencyRecord status: "completed". Queue entry: removed from pending set. Checkpoint deleted (no longer needed).

Client polls GET /refund/{task_id}

Redis hit → full result returned instantly. If Redis TTL expired → TaskResult DB. If not found there → IdempotencyRecord status. Final fallback: not_found.

Agent Deep Dive

🔀 Supervisor Agent

Role: Orchestrator. Decides which agent to call next based on current state.

How: Uses LLM with tool_choice="any" bound to 4 routing tools. The LLM must call exactly one tool per turn.

Guards (checked before LLM call):

  • hitl_required=True in state → immediately route to HITL (no LLM call needed)
  • cycle_count > MAX_CYCLES (15) → route to HITL with reason "cycle limit exceeded"
  • Per-agent retry count > MAX_RETRIES (3) → route to HITL with reason "retry_exhausted:agent"
  • LLM itself throws an error → route to HITL

Routing tools:

Tool Called When
call_validation_agent validation_passed is None
call_policy_agent validation_passed=True AND decision is None
call_communication_agent decision is set AND request_saved ≠ True
finish_workflow validation_passed=False OR request_saved=True

✅ Validation Agent

Role: Verifies customer identity, account standing, and order legitimacy.

Tools (parallel wave execution):

  • Wave 0 (parallel): lookup_customer(email) + get_order_details(order_id)
  • Wave 1 (parallel): get_customer_analytics(customer_id) + verify_order_ownership(order_id, customer_id)

Business rules checked:

  • Customer exists (found=True)
  • Account status is "active"
  • Order exists (found=True)
  • Order belongs to customer (ownership.valid=True)
  • Order status is "delivered"
  • Risk score from analytics < 0.8

Failure handling: ReactMaxIterationsError or JSON parse error → sets hitl_required=True.

📋 Policy Agent

Role: Determines refund eligibility and calculates the exact refund amount based on warehouse policies.

Tools:

  • Wave 0 (7 tools in parallel): search_policies (Pinecone vector search), check_refund_history, check_eligibility, get_product_return_policy, get_customer_order_summary, get_refund_rate_by_category, get_similar_refund_decisions
  • Wave 1: calculate_refund (depends on check_eligibility output as eligibility_result param)

Tier rules:

Tier Window Extension Restocking Fee Max Refunds/Year
Gold +15 days Fully waived 5
Silver +7 days 50% waived 3
Bronze None Full fee applies 2

Warehouse category policies: electronics (15d, 15% fee), industrial_equipment (60d, 10% fee), raw_materials (30d, 5%), chemicals (7d, 20%), food_perishables (3d, 0%), packaging (30d, 5%), furniture (30d, 10%)

💾 Communication Agent

Role: Persists the final decision and updates all related records for audit compliance.

Tools (all parallel — single wave):

  • save_processed_request — upsert to processed_requests table; dedup via SAVEPOINT guard on refund_request_id unique constraint
  • update_customer_analytics — recalculates risk_score, refund_rate, total_spent; idempotent per refund_request_id (checks analytics_updated flag)
  • update_refund_request_status — updates status on original refund_requests row
  • log_audit_event — inserts audit_logs row for compliance

On DB failure: sets hitl_required=True so a human can retry or compensate. Does NOT set request_saved=True — prevents supervisor from marking workflow done when data wasn't persisted.

ReAct Pattern with Parallel Wave Execution

The custom ReAct engine in agents/react_loop.py goes beyond standard sequential tool execution. It uses a topological wave sort to run independent tools in parallel.

How the ReAct Loop Works

  1. LLM called with system prompt + current messages
  2. If LLM returns no tool calls → it's the final answer, return response content
  3. If LLM returns tool calls → compute execution waves using dependency map
  4. Execute only Wave 0 in parallel using asyncio.gather()
  5. If LLM smuggled dependent tools into Wave 0, trim the AIMessage to only Wave 0 calls (prevents dangling tool_call_id errors)
  6. Append ToolMessage results to message history
  7. Loop: LLM sees tool results, generates next iteration (may call Wave 1 tools)
  8. Repeat until final text response or max_iterations (8) hit

Dependency Map Example (Validation Agent)

VALIDATION_DEPS = {
    "lookup_customer":        [],            # Wave 0 — no deps
    "get_order_details":      [],            # Wave 0 — no deps
    "get_customer_analytics": ["lookup_customer"],  # Wave 1 — needs customer_id
    "verify_order_ownership": ["lookup_customer"],  # Wave 1 — needs customer_id
}

Wave 0 runs lookup_customer and get_order_details simultaneously. The LLM then sees both results and calls get_customer_analytics and verify_order_ownership with the now-known customer_id. Wave 1 also runs them in parallel.

Why Only Execute Wave 0 Per LLM Turn?

If the LLM decides to batch Wave 0 + Wave 1 tools in a single response (it shouldn't, but might), executing dependent tools immediately would cause hallucinated arguments — the LLM can't know customer_id before lookup_customer returns. We trim to Wave 0 only and let the next LLM iteration generate Wave 1 with real values.

ReactMaxIterationsError → HITL Escalation

If the loop exhausts max_iterations=8 without a final answer, it raises ReactMaxIterationsError. Each agent catches this and returns hitl_required=True with reason "react_max_iter:{agent}".

Dual-Layer Idempotency

Prevents duplicate processing of the same refund request, even across server restarts or Redis flushes.

Layer 1: Redis (sub-millisecond)

Key: idempotency:{sha256(email:order:reason)}
Value: task_id
TTL: 24 hours

Fast path. Checked on every POST /refund before any DB access.

Layer 2: PostgreSQL IdempotencyRecord

Table: idempotency_records with unique constraint on idempotency_key.

Guard against Redis flush/restart. Also catches race conditions via IntegrityError handling.

Race Condition Handling

Two simultaneous identical requests can both pass the Redis check (cache miss) and race to write the DB. The IntegrityError on the unique constraint is caught, the losing request rolls back, then reads the winner's task_id and returns it as "duplicate". This is the correct CRDT-style pattern.

Idempotency Key Sources

  • Client-supplied: idempotency_key field in request body — client controls dedup window
  • Server-derived: sha256 of email:order_id:reason — content-based dedup

Dual-Layer Checkpointing

After every agent node completes, the full workflow state is saved to two stores. This enables crash recovery without re-running already-completed agents.

Custom Checkpoint Store (checkpoint/store.py)

Redis: wf_checkpoint:{thread_id} → JSON payload with full state (messages excluded — not JSON-safe). TTL 24h. Fast path for recovery.

PostgreSQL: workflow_checkpoints table, upsert on thread_id. Permanent, survives Redis flush. Used as cold-start fallback.

Both writes are best-effort — failure logs a warning but never disrupts the workflow.

LangGraph Internal Checkpoint (AsyncPostgresSaver)

LangGraph's own checkpointer uses a separate PostgreSQL connection. Activated by passing configurable: {thread_id} in the graph config.

This stores the full LangGraph graph snapshot including message history, allowing mid-node resume.

On HITL approve, this checkpoint is explicitly deleted before re-running, so the workflow starts fresh with reset state rather than resuming from the stale HITL-triggering state.

State Serialization

The _serialize_state() function strips the messages field (contains LangChain BaseMessage objects that aren't JSON-serializable) before saving. On restore, messages are reconstructed from scratch.

Checkpoint Deletion on Success

Once request_saved=True or compensated=True and hitl_required is not set, the checkpoint is deleted from both Redis and PostgreSQL. This prevents a stale checkpoint from being incorrectly resumed if the thread_id were ever reused.

Crash Recovery

If the server process is killed mid-workflow, the task queue in Redis preserves all in-progress tasks. On restart, the startup() hook automatically recovers them.

Recovery Flow

  1. task_queue.get_incomplete_tasks() reads all task_ids from refund:tasks:pending set
  2. Skip tasks with status=hitl_pending — these need human action, not auto-restart
  3. For each recoverable task: asyncio.create_task(_recover_task(payload))
  4. _recover_task wraps _process_refund with exception logging
  5. _process_refund calls run_workflow(thread_id=task_id)
  6. run_workflow calls load_checkpoint(redis, thread_id)
    • Redis hit → loads last state, injects as initial_state
    • Redis miss → PostgreSQL fallback via WorkflowCheckpoint table
  7. LangGraph supervisor receives injected state. Already-set fields (validation_passed=True, decision="approved", etc.) cause the LLM to route directly to the next incomplete agent

Key insight: Recovery works because the supervisor's routing rules are purely state-driven. Injecting the recovered state is equivalent to telling the supervisor "these agents already ran — what's next?" The supervisor LLM naturally skips completed work.

Human-In-The-Loop (HITL)

When the AI system cannot safely resolve a request, it escalates to human review. This covers edge cases, errors, and situations requiring judgment beyond configured rules.

HITL Triggers

  • Supervisor cycle_count > 15 — workflow looping without progress
  • Supervisor Agent retry count > 3 for any single agent
  • Supervisor LLM call itself throws an exception
  • Validation ReactMaxIterationsError (tools not converging) or JSON parse error
  • Policy ReactMaxIterationsError or JSON parse error
  • Communication DB write failure or ReactMaxIterationsError

HITL Node Behavior

  • Upserts a HITLTask row to PostgreSQL with full state_json snapshot
  • Sets request_saved=True to prevent the supervisor from looping (workflow ends)
  • Keeps the LangGraph checkpoint — needed if a human approves and re-runs
  • Stores result in Redis (24h TTL) and TaskResult table (permanent)

Human Resolution Actions

Action What Happens
approve Load HITLTask.state_json. Reset cycle_count=0, agent_retry_counts={}, hitl_required=None, request_saved=None. Delete stale LangGraph PG checkpoint. Re-enqueue task. Re-run _process_refund with recovered state via background task.
deny Write decision=denied, refund_amount=0 directly to Redis + TaskResult DB. Update IdempotencyRecord + HITLTask. No re-run.
compensate Write decision=denied, refund_amount=0, compensated=true. Same storage writes. Used when the error itself justifies giving the customer something (handled manually).

HITL API Endpoints

  • GET /hitl/tasks?status=pending — list all tasks needing review, includes full state snapshot
  • POST /hitl/tasks/{task_id}/resolve — resolve with action + optional note and resolved_by

3-Layer Result Storage

Results are stored in three places with different durability/speed trade-offs. GET /refund/{task_id} tries them in priority order.

Layer Store TTL Use Case
1 (fastest) Redis task:{task_id} 1h (success) / 24h (HITL) Normal result polling; sub-millisecond reads
2 (permanent) PostgreSQL task_results Forever After Redis TTL expires; includes full decision details; source: "db"
3 (status only) PostgreSQL idempotency_records Forever Minimal status when TaskResult not yet written; source: "idempotency_db"

The TaskResult table was specifically added because Redis TTL of 1h is too short for clients that poll hours later. It persists the complete decision record permanently.

Vector Policy Search (Pinecone)

The Policy Agent's search_policies tool uses semantic similarity to find relevant warehouse return policy documents, rather than exact keyword matching.

Pinecone Setup

  • Index: warehouse-refund-policies (serverless, AWS us-east-1)
  • Dimensions: 384 (all-MiniLM-L6-v2)
  • Metric: cosine similarity
  • 8 policy documents indexed: general, electronics, furniture, gold/silver/bronze tiers, fraud policy, eligibility policy
  • Index built at startup via build_policy_index()

Semantic Cache Layer

Before hitting Pinecone, queries are checked against a Redis semantic cache. The same (or semantically similar) query reuses cached embedding results, reducing latency and Pinecone API calls.

Cache: query string → policy docs JSON, stored in Redis.

Why Vector Search for Policies?

Policy queries from the LLM are natural language (e.g., "What is the return window for damaged industrial equipment for gold tier?"). Exact keyword matching would miss semantically equivalent phrasings. Vector similarity returns the most contextually relevant policy documents regardless of wording.

Guardrails-AI Module & Input/Output Protection

Four layers of protection ensure safe LLM interactions: input sanitization, PII masking, guardrails-ai validation, and output parsing. All guards are traced to LangSmith via OpenTelemetry spans.

🛡️ Prompt Injection Guard

File: guardrails/input_sanitizer.py

Defense-in-depth strategy with 4 layers:

  1. Character filtering — strips control chars (0x00–0x1F) and Unicode direction overrides (U+200B–U+206F)
  2. Length enforcement — truncates at 500 chars to prevent token-stuffing
  3. Pattern detection — 18 regex patterns catching known injection signatures (e.g., "ignore previous instructions", "system prompt:", "[INST]")
  4. Delimiter wrapping — wraps user text in <<<USER_INPUT>>>...<<<END_USER_INPUT>>> so the LLM treats it as data, not instructions

Two modes:

  • raise_on_injection=True (API layer) — rejects the request with a 200 + error response
  • raise_on_injection=False (workflow layer) — neutralizes keywords in-place (e.g., "ignore" → "[ignore]") and continues

🔒 PII Masking

File: guardrails/pii_handler.py

Detects and masks 5 PII types before data flows through LLM prompts:

Multi-strategy JSON extraction replaces fragile split("```json") logic:

Resilience: Circuit Breaker, Retry Budget & Model Fallback

Production-grade failure handling in executor/resilience.py. Prevents cascading failures and enables automatic LLM provider failover with budget-limited retries.

🔌 Circuit Breaker

Pattern: Fail-fast when provider is down

State Behaviour
CLOSEDNormal operation; count consecutive failures
OPENAll calls rejected immediately (30s cooldown)
HALF_OPENOne test call; success → CLOSED, failure → OPEN

Config: 5 failures to trip, 30s recovery, 2 successes to close. Each model has its own independent circuit breaker.

💰 Retry Budget

Pattern: Token-bucket retry limiter

  • Max 20 retries per 60-second rolling window
  • Retry ratio cap: retries ≤ 10% of total requests
  • Exponential backoff: base * 2^attempt * jitter
  • Budget exhaustion → RetryBudgetExhausted exception

Prevents thundering herd during outages — system degrades gracefully.

🔄 Model Fallback Chain

Pattern: Automatic failover between LLMs

Primary: llama-3.1-8b-instant
  ↓ circuit open / error
Fallback Fast: llama-3.1-8b-instant (alt endpoint)
  ↓ circuit open / error
Fallback Large: llama-3.3-70b-versatile

LangSmith Visibility:

  • fallback.model_used — which model actually served the request
  • fallback.attempt — how many models were tried
  • GET /resilience/health — real-time circuit states

Key Design Patterns & Decisions

🔀 Supervisor Pattern (not pipeline)

Rather than a fixed pipeline (validation → policy → communication), a supervisor LLM decides the route. This allows the flow to adapt: if validation fails, supervisor directly ends without running policy or communication.

⚡ Parallel Wave ReAct

Standard ReAct runs tools one at a time. Our topological wave sort groups independent tools and runs each wave with asyncio.gather(). For the policy agent, this runs 7 tools simultaneously instead of 7 sequential round-trips to the LLM.

🛡️ Best-Effort Writes

Checkpoint saves, audit logs, and telemetry spans are all wrapped in try/except. A failure to save a checkpoint logs a warning but never raises — the workflow continues. Correctness trumps observability.

🔒 SAVEPOINT Dedup in Communication

save_processed_request uses PostgreSQL SAVEPOINTs to handle race conditions. The outer transaction stays alive even if an inner INSERT fails with IntegrityError on the unique constraint.

📍 DB-First Idempotency

IdempotencyRecord is written to PostgreSQL before Redis cache. This ensures that even if the process crashes between the DB write and the Redis write, the DB record prevents duplicate processing on recovery.

🚫 No request_saved on Failure

The communication agent deliberately does NOT set request_saved=True on DB failure. This is critical: it routes to HITL rather than telling the supervisor the workflow is done when data wasn't persisted.

📤 Async Background Tasks

FastAPI's BackgroundTasks runs _process_refund after the HTTP response is sent. The client receives a task_id immediately and polls for results. This prevents HTTP timeout for long-running AI workflows.

♻️ State-Driven Recovery

On crash recovery, the system injects the last saved state as the initial state. The supervisor LLM naturally routes to the next incomplete agent because the state fields for already-completed agents are already set. No special recovery logic needed.

Interview Q&A

Click each question to expand the answer.

Why LangGraph instead of a simple Python pipeline?

LangGraph provides a stateful directed graph with built-in checkpointing, conditional routing, and the ability to resume from any node after a crash. A simple pipeline would require manual state management, crash recovery, and retry logic. LangGraph's StateGraph lets us define the workflow declaratively while the framework handles state merging, cycle detection, and persistence via the checkpointer. The supervisor pattern also allows the routing logic to be entirely LLM-driven — we don't hardcode which agent runs after which.

How does the system handle duplicate refund requests?

Two layers of idempotency. First, Redis is checked as a sub-millisecond fast path using an idempotency key (either client-supplied or sha256-derived from the request payload). If Redis misses (e.g., after a Redis restart), we fall back to a PostgreSQL IdempotencyRecord table. If both miss, it's a new request. Race conditions between two simultaneous identical requests are handled by catching the IntegrityError from the unique constraint and returning the winner's task_id. The DB is written first (before Redis) to ensure durability even if the process crashes between the two writes.

What happens if the server crashes mid-workflow?

The Redis task queue persists every in-progress task. On startup(), we call get_incomplete_tasks() which reads the refund:tasks:pending set from Redis. For each task (excluding HITL-pending ones which need human input), we call _recover_task(). This invokes run_workflow() with the same thread_id. Inside, we call load_checkpoint() which tries Redis first, then PostgreSQL. The recovered state is injected as the initial state. The supervisor LLM sees the already-set fields and routes directly to the first incomplete agent — no work is repeated.

What is the ReAct pattern and how is it used here?

ReAct (Reason + Act) is a prompting pattern where the LLM alternates between reasoning about what to do and acting by calling tools. In our system, each agent runs a ReAct loop: the LLM is given a system prompt and user message, it calls tools, sees the results, reasons again, and eventually produces a structured JSON answer (no more tool calls). The key innovation here is parallel wave execution: instead of calling tools one at a time (standard ReAct), we group independent tools by dependency and run each group simultaneously with asyncio.gather(). This cuts latency significantly — the policy agent's 7 independent tools run in one parallel batch.

When does HITL trigger and what can a human do?

HITL triggers in five scenarios: (1) supervisor cycle count exceeds 15, (2) any agent exceeds 3 retries, (3) supervisor LLM throws an exception, (4) any agent hits ReAct max iterations (8 tool-calling loops without convergence), (5) communication agent's DB writes fail. The hitl_node saves the full state to the hitl_tasks table and ends the workflow. A human can then: approve (reset counters, delete stale LangGraph checkpoint, re-run workflow), deny (write denied result directly), or compensate (write compensated result with refund_amount=0 — used when the error itself warrants manual handling).

How do you ensure the communication agent doesn't double-write on retry?

Three levels of idempotency in the communication agent: (1) save_processed_request has a PostgreSQL SAVEPOINT pattern — it checks for an existing record first, and if an IntegrityError occurs on the unique refund_request_id constraint during a race, it rolls back only the savepoint (not the outer transaction) and reads the winner. (2) update_customer_analytics checks the analytics_updated flag on the ProcessedRequest row before recalculating — if already updated for this refund_request_id, it skips. (3) All four communication tools run inside a single LangGraph ReAct loop pass, and the supervisor won't re-route to communication once request_saved=True.

Why are there two checkpoint systems (custom + LangGraph)?

They serve different purposes. The custom checkpoint store (checkpoint/store.py) is an explicit agent-level snapshot of the RefundState dict, saved after each agent completes. It's used for our custom crash recovery logic — we control exactly what's saved and when. The LangGraph AsyncPostgresSaver is LangGraph's internal mechanism that stores full graph execution snapshots (including message history) and allows graph-level resume by thread_id. When HITL approve re-runs the workflow, we explicitly delete the LangGraph internal checkpoint (because it contains the old cycle count and hitl_required=True) and inject our own recovered state — giving us full control over the resume state.

How does the policy agent use vector search?

The search_policies tool embeds the query using HuggingFace all-MiniLM-L6-v2 (384 dimensions), then queries a Pinecone serverless index (warehouse-refund-policies) using cosine similarity to find the top 3 most relevant warehouse policy documents. Before embedding, it checks a Redis semantic cache — if the query (or a similar one) was recently made, it returns cached results. This avoids unnecessary Pinecone API calls and re-embedding the same query. At startup, 8 policy documents are upserted into Pinecone covering general, electronics, furniture, tier-specific, fraud, and eligibility policies.

How is the supervisor's routing implemented — is it hardcoded?

No, it's LLM-driven. The supervisor uses llm.bind_tools(ROUTING_TOOLS, tool_choice="any") which forces the Groq LLM to always call exactly one of the four routing tools (call_validation_agent, call_policy_agent, call_communication_agent, finish_workflow). The LLM receives the current state summary and the tool descriptions (which encode the routing rules) and decides which to call. This means the routing logic lives in the prompt and tool descriptions — not in Python conditionals. Safety guards (cycle cap, retry cap, hitl_required pass-through) are applied in Python before the LLM call so they can't be bypassed.

How do you prevent the GET /refund endpoint from returning stale data?

The 3-layer storage design handles this. Redis (Layer 1) is the hot cache with a 1h TTL for completed results. When Redis expires, the TaskResult PostgreSQL table (Layer 2) serves as the permanent record — it's written by _persist_task_result() immediately after every workflow completion, so it's always available. The IdempotencyRecord (Layer 3) provides a status-only fallback even if TaskResult hasn't been written yet. This ensures results are always available even after Redis TTL expiry, server restarts, or partial write failures.

Describe the database schema and key tables.
  • customers — name, email, tier (gold/silver/bronze), account_status, total_orders, total_refunds
  • products — name, category, price, return_window_days, restocking_fee_pct
  • orders — FK to customer + product, purchase_date, amount, status, payment_method
  • refund_requests — FK to order + customer, reason, status (pending→approved/denied)
  • processed_requests — final decision record with unique constraint on refund_request_id; has analytics_updated flag for idempotency
  • customer_analytics — risk_score, refund_rate, total_spent (recalculated per request)
  • audit_logs — per-tool-call log: agent_name, tool, input/output JSON, status, duration_ms
  • prompt_registry — versioned prompt storage with is_active flag; unique(name, version)
  • idempotency_records — dedup table; unique(idempotency_key)
  • task_results — permanent outcome store; unique(task_id)
  • hitl_tasks — pending human review tasks with full state_json snapshot
  • workflow_checkpoints — custom agent-level checkpoints; unique(thread_id)
How would you scale this system?
  • Multiple API workers: FastAPI with multiple Uvicorn workers; Redis and PostgreSQL are shared state so workers coordinate naturally via the task queue
  • Dedicated worker processes: Move _process_refund to a Celery or ARQ worker pool; API layer only handles HTTP and task enqueuing
  • LLM concurrency: Each task uses its own LLM instances; Groq's rate limits are the current bottleneck — a queue depth limit or token bucket would be added
  • Read replicas: Customer/order lookups (read-heavy) could be routed to PostgreSQL read replicas
  • Pinecone auto-scales: Serverless index handles variable load automatically
  • Redis Cluster: For high throughput, shard the queue hash across Redis nodes
How do you prevent prompt injection attacks?

Defense-in-depth with four layers. First, we strip control characters and Unicode direction overrides that could manipulate text rendering. Second, we enforce a 500-character limit to prevent token-stuffing. Third, we run 18 regex patterns detecting known injection signatures like "ignore previous instructions", "system prompt:", "[INST]", "act as", etc. Fourth, we wrap surviving user text in <<<USER_INPUT>>>...<<<END_USER_INPUT>>> delimiters so the LLM treats it as data rather than instructions. At the API layer, detection raises immediately (reject the request). Inside the workflow, we neutralize keywords in-place (e.g., "ignore" → "[ignore]") and continue processing.

How is PII handled before sending data to the LLM?

We use regex-based PII detection covering emails, phone numbers, credit cards, SSNs, and IP addresses. Two masking modes exist: irreversible (mask_pii()) for LLM-bound data where we never need the original back, and reversible (PIIMasker class) that maintains a token→original lookup table for internal logging where we might need to correlate back. Emails are partially masked (preserving domain for debugging), while other PII types are fully redacted. The masking runs at the workflow entry point (graph.py) and again at the policy agent level where refund_reason is directly included in the LLM prompt.

Why use a multi-strategy output parser instead of LangChain's built-in?

Our agents use tool-calling LLMs (Groq/Llama) in a ReAct loop, so the final "answer" comes as free-text after tool execution — not as a structured tool call. LangChain's JsonOutputParser expects a specific prompt format that doesn't fit our ReAct pattern. Our parser tries three strategies in order: (1) direct json.loads() on the full response, (2) regex extraction from ```json fences, (3) character-by-character brace-depth matching to find the first complete JSON object. After extraction, we validate with Pydantic models (typed fields, ranges, required keys). This handles the variety of LLM output formats without depending on the model always following a specific format perfectly. On failure, we raise AgentOutputParseError which routes to HITL or error handling rather than crashing silently.
